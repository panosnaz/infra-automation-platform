# Platform Status and Pending Items

This is the **current, authoritative status tracker** for the Network Platform Engineering Platform. It exists so an AI agent (or engineer) starting a new session can quickly answer: *what's already done, what's known-broken, what's intentionally deferred, and what needs a decision before proceeding?*

> **Supersedes [`Current-State-v1.md`](archive/Current-State-v1.md) for status purposes.** That document is dated 2026-07-04 and describes Platform v1 (Platform API, n8n orchestration, no MCP Server, no Execution Framework) — it predates [ADR-016](../adr/ADR-016-Platform-v2-Replacement-Architecture.md) through [ADR-021](../adr/ADR-021-VXLAN-EVPN-Domain-Expansion.md) entirely and should not be trusted as current. It has been moved to `architecture/archive/` alongside the other superseded Platform v1 documents, not deleted. This document is updated instead, going forward.

> **Per [`knowledge/README.md`](../README.md)'s rule, this vault never contains live infrastructure state** — no live tenant counts, object UUIDs, or point-in-time snapshots. Everything below is a durable fact about the platform's *build status*, not a data export. For live counts/IDs, query Nautobot/GitLab directly.

- **Fabric inventory — Nautobot DCIM is now the authoritative node roster (2026-09-14, live-verified).** The generator never queried DCIM Devices at all, so every `topology/pod-N/paths-M/pathep-[ethX/Y]` DN was built from free-form integers hand-typed into JSON Custom Fields with nothing validating them — and the APIC accepts a DN naming a switch that does not exist, leaving it silently `unformed`. Added `_QUERY_DEVICES`/`get_devices()`, a new `apic.fabric_inventory.nodes[]` YAML key (sorted by node_id for the determinism gate), and **fatal** validation (`FabricInventoryError`) of every static-path and L3Out node reference against the roster. Also closed the `aci_pod_id` gap: the Custom Field existed but no tool could write it, so multi-pod fabrics were unmodelable. Live-verified end to end — `spine-1` (node 1001, pod 1, serial `FDO2306FG77`) created via the real `create_fabric_device` tool, pod IDs backfilled on `leaf-a`/101 and `leaf-b`/102, then determinism + `validate_nac` + OPA + `terraform plan` all green on the new shape. See ADR-020's fabric-inventory section. **Does not give the APIC a working switch** — see §2.
- **L4-L7 / PBR / Service Graph gap closure — live-verified apply + destroy (2026-09-15).** Four gaps found by auditing the layers against each other; see ADR-020's Phase H follow-up for full detail and evidence. (1) **Service Graphs had no function node** — `aci_l4_l7_service_graph_template` creates only the graph shell and terminals, and `aci_function_node` was never used, so every graph produced had nothing between its terminals and could not render. APIC accepts that silently. This was a correctness bug, not a missing feature. (2) `trunking`/`promiscuous_mode` had Terraform lookups but no MCP field or client argument, so both always resolved `null` — dead capability. (3) PBR had no health group, IP SLA, thresholds or hashing, and `create_pbr_policy` accepted only one destination although the YAML and Terraform had always supported a list. (4) **A PHYSICAL L4-L7 device could not be created at all** — the provider makes `relation_vns_rs_al_dev_to_phys_dom_p` mandatory for PHYSICAL and only the VMM relation existed; found solely by running a real plan. Closed with 2 new MCP tools (`create_pbr_health_group`, `create_ip_sla_policy`), multi-destination PBR (single-destination form kept as normalised shorthand), and an explicit WARNING in the tool response when no destination is health-tracked. **Evidence: `Plan: 31 to add` → `Apply complete: 31 added` → direct APIC verification with every relation `state: formed` → `Destroy complete: 31 destroyed`.** Fixture: `platform/terraform/aci/tests/fixtures/l4l7-pbr-resilient.yaml`. **CORRECTED 2026-09-15 — that evidence was not sufficient and the "live-verified" claim was too strong.** Object existence plus `state: formed` does not mean APIC considers the configuration valid; re-checking the same apply with a fault delta found 11 new faults nobody had looked at, including an invalid L4-L7 device. See the 2026-09-15 entry below.
- **Concrete devices modelled; PHYSICAL L4-L7 floor is 6 faults on this simulator (2026-09-15, measured).** `aci_concrete_device`/`aci_concrete_interface` plus the logical interface's `relation_vns_rs_c_if_att_n` binding take the L4-L7 fault count 10 → 6 and clear every structural fault (`vnsRsCIfAttN` reports `formed`). **6 is the floor and is unavoidable:** tested with the path attachment present (`unformed`) and omitted entirely — both give 6, the latter with an explicit `cdev-missing-path-for-interface`. A concrete device is an appliance plugged into a switch port, and this fabric has no switches. Decision: keep the code (correct, and needed the day real ports exist), accept the floor, and **do not add an allowlist** — read any count above 6 on this scope as a real regression. Note also that `aci_concrete_interface`'s own path-attachment attribute PRE-VALIDATES the target and fails the apply, unlike `aci_l3out_path_attachment`; the path is therefore set via `aci_rest_managed`, matching what raw REST accepts. Provider-side validation is inconsistent between resources — test each, do not generalise.
- **PBR lab built end-to-end from MCP tools to APIC (2026-09-15) — applied, and the fault delta says it is a failed deployment.** The lab in `docs/Configure PBR LAB.docx`, built under a standing no-delete constraint. `93 to add, 0 to change, 0 to destroy` → `93 added, 0 destroyed` → **`FAIL: 10 new faults`**. This is the first time the L4-L7/PBR scope has been driven all the way from MCP tool calls through Nautobot and the generator to a real apply, rather than from hand-written fixture YAML. Four things came out of it, all recorded in ADR-020's PBR lab section: **(1)** The earlier "virtual L4-L7 apply is blocked on a vCenter password and reachability" conclusion was **wrong** — a VMM domain needs no controller, which removes the vCenter dependency entirely; `vCenter_VMM` exists in APIC with 0 `vmmCtrlrP` and the device's `vnsRsALDevToDomP` is `formed`. **(2)** But it does not reach zero faults: **10 is the floor** for a virtual L4-L7 device with no vCenter, all rooted in `vnsConfIssue-missing-cdev`, and an A/B probe proved adding a `vnsCDev` holds it at 10 while trading the faults for worse vCenter-vNIC ones (F1778/F0765). Same shape of hard floor as physical (6, no leaf ports), different cause. **(3)** `check_apic_faults.py` was **blind to every object outside a tenant** — VMM domains, VLAN pools, domains, AEPs, the whole access-policy hierarchy. This apply raised 7 faults there and the check reported none; all 7 were `cleared`, so nothing was missed, but only by luck. Fixed with `managed_global_objects()`. **(4)** The generator crashed outright on a **declared-but-unset** Custom Field (`.get(key, {})` does not default an explicit `None`) — fixed with a regression test. **Finding F-01 also reproduced live**: the first L4-L7 writes were silently discarded because `aci_l4l7_services` was undeclared. Four Custom Fields had to be declared before any of this persisted. The apply additionally covered the ported access-policy and protocol-L3Out scope — previously "plan-verified only, no apply run" — with **zero new faults**; see `Evidence-Matrix.md` §2.
- **`create_concrete_device` added (2026-09-15) — the missing link that made L4-L7 devices undeployable.** The PBR lab apply left an invalid L4-L7 device rooted in `vnsConfIssue-missing-cdev`, and the fix was unexpressible: `main.tf` had accepted `vnic_name` since the concrete-device work landed, but a repo-wide grep found **exactly one** occurrence — in `main.tf` itself. No MCP tool, no generator path, no fixture produced it, and `create_l4l7_device` does not accept concrete devices. The new tool writes `vnsCDev` + `vnsCIf` behind an existing logical device **and** wires each concrete interface to a logical one (`relation_vns_rs_c_if_att_n`) — that binding is the part that clears "LIf has no relation to CIf", so a concrete device written without it fixes nothing. Unlike every other `create_*`, it edits an existing entry rather than appending, so it refuses a missing parent device or an unknown logical interface rather than writing orphaned intent (the same silent-no-op shape as finding F-01). **A VIRTUAL concrete device requires a VMM domain WITH a controller** — the schema refuses the controller-less combination, because that was measured to hold the fault count at 10 while trading the faults for worse ones (F1778/F0765). **Plan-verified** (`tests/fixtures/l4l7-concrete-virtual.yaml`: `Plan: 30 to add`, `vmm_controller_dn` + both `vnic_name`s reaching the provider, **0 `pathep-` references**), **not live-verified**: VIRTUAL needs a real vCenter with the appliance VM present, PHYSICAL needs leaf switches. A live Nautobot write was attempted and could not run — Docker Desktop stopped mid-session, taking Nautobot and Vault with it. Catalogue 50 — 51; see ADR-020.
- **L3Out Logical Interface Profile sub-policies implemented and live-verified (2026-09-16).** Until this, an `l3extLIfP` this platform created carried a name and a description and nothing else. That was not obviously broken, because APIC auto-creates every policy relation on a new profile pointing at `uni/tn-common/<kind>-default` — so profiles were never unconfigured, they silently ran on fabric defaults with no way to change them. Now covered: **ND, Data Plane Policing (ingress + egress), PIM v4, PIM v6, IGMP, Custom QoS, and the profile's own QoS priority** — every policy the provider can both create and bind. 6 new MCP tools (catalogue 51 — 57), 5 new Terraform resources, a new `aci_interface_policies` Custom Field (declared in Nautobot BEFORE any write, per Definition of Done item 2), and fatal generator validation of every policy reference. **Live-verified at both layers**: Terraform `19 to add` — `19 added` — `19 destroyed` on a throwaway tenant with all seven relations read back at `state: formed` and attribute values spot-checked, one fault (`F1298`, the known switch-absence family from the fixture's external EPG, not from any policy), zero leftovers after destroy; and all six tools driven over real MCP JSON-RPC against the running container, writes confirmed in Nautobot, generator run end to end. **Three assumptions the apply disproved, none catchable by a plan**: the relations take a **DN, not a name** (all seven failed at once after a clean plan); the literal `default` is **rejected** (omit the field to inherit APIC's default); and the DN prefixes are inconsistent (`igmpIfPol-` is camelCase while the other four are lowercase), so `main.tf` resolves through each resource's `.id` rather than building DN strings. ARP and NetFlow are deliberately excluded — see ADR-020 for why each is blocked differently.
- **Two pre-existing platform bugs found by driving tools over the real MCP protocol (2026-09-16).** Both had shipped; both were invisible to the unit suites because those call handler functions directly. **(1) Optional fields declared with `default_factory` were advertised as REQUIRED over MCP** — `field_info.default` is `PydanticUndefined` for such fields, not the factory's value, so any client omitting them got `Field required`. **11 fields across 9 tools**, including `create_epg` and `create_aep`, both already marked live-verified. Fixed in `main.py` with `get_default(call_default_factory=True)`, guarded by a new registry test. **(2) Four L3Out mutators reported success while writing nothing** — `create_l3out_node_profile` returned OK and left no `node_profiles` key at all. pynautobot diffs a record against its own cached state, and `list(...)` is a shallow copy, so mutating the nested dicts mutated the cache too and the diff sent nothing. Fixed with `copy.deepcopy` in all five mutators. This is finding F-01's failure shape — a write that reports success and silently does nothing — arriving through an entirely different mechanism.
- **Route control / route maps implemented and live-verified (2026-09-16).** The platform had **no** route-control support at all — no Terraform resource, no MCP tool, no generator key — while the provider had all four pieces the whole time. Built for the transit-routing lab, whose requirement was to stop using per-subnet Export Route Control Subnet flags and drive export from a route map. A route map is four objects (`rtctrlSubjP` match rule, `rtctrlMatchRtDest` prefix, `rtctrlProfile` map, `rtctrlCtxP` ordered entry); match rules are tenant-scoped, maps hang off an L3Out. 4 new MCP tools (catalogue 57 — 61), 5 new Terraform resources, a new `aci_route_control` Custom Field, and fatal generator validation of every match-rule and route-map reference. **Two properties drive the design**: an ACI route map ends in an **implicit deny**, so a map matching nothing advertises nothing with no fault (hence the fatal reference check); and a **custom-named map is inert** until bound — only `default-export`/`default-import` apply on their own, so `create_route_control_profile` warns for any other name. **Live-verified**: `8 to add, 8 to change, 0 to destroy` applied with **zero new faults** (25 before, 25 after), every MO read back — both match rules with the screenshots' exact defaults, `rtctrlProfile` at `type=global`, both contexts' match-rule relations `formed`, and the `l3extRsInstPToProfile` export binding `formed`.
- **Two prerequisites for the above, neither of which existed (2026-09-16).** **(1) BD subnet `public` scope was hardcoded `False`** in `_build_bridge_domains()`, so no bridge domain this platform ever created could be advertised out of an L3Out. **(2) `fvRsBDToOut` was not modelled anywhere** — and a public subnet with no L3Out association is still never advertised, so the two only work together. Both added, with the negative test asserting every pre-existing BD keeps its private/no-association shape.
- **The DN-not-name provider trap recurred twice more, and is now a stated rule (2026-09-16).** `relation_rtctrl_rs_ctx_p_to_subj_p` and `relation_fv_rs_bd_to_out` both take DNs despite the MOs using `tnXxxName`, and `aci_match_route_destination_rule.aggregate` takes `"yes"`/`"no"` rather than a boolean. **None of the three was catchable by a plan** — the plan renders whatever it is given and only the apply fails. Rule: in this provider assume a `relation_*` attribute wants a DN and a boolean-looking attribute wants `"yes"`/`"no"`, and never read a clean plan as evidence about either.
- **INCIDENT: a test fixture deleted a shared global object out from under production intent (2026-09-16).** `ExtL3Dom` was found missing, with both `sales` L3Outs at `state=missing-target`. Cause: the previous day's interface-policy fixture named `domain: ExtL3Dom` — a **globally-scoped** object the real L3Outs also use — and ran in an isolated state directory, so its `terraform destroy` deleted it. Restored by a targeted apply; both relations returned to `formed`. The fixture now uses its own `IfPol_L3Dom`. **`check_apic_faults.py` could not have caught this**: it is scoped to managed tenants plus the non-tenant objects the *current* deployment declares, an object deleted by a different state file is outside both, and a `missing-target` relation raises no fault at all. Fault checking is not drift detection, and **nothing in this platform currently detects drift**.
- **A permanent non-converging `terraform plan`, found and fixed (2026-09-16).** After the PBR lab, plan never reached zero changes: APIC returns `>`/`<` in descriptions HTML-escaped (`\u003e`) and MAC addresses upper-cased, so Terraform re-proposed the same edits forever — apply succeeded, next plan showed them again. That destroys the "clean plan" signal and buries real drift. Fixed in the intent (no `<`/`>` in descriptions, MACs stored upper-case). **Two pre-existing non-converging diffs remain**, both unrelated: `aci_function_node` keeps setting `l4_l7_device_interface_consumer_name`/`provider_name` which APIC does not return (a symptom of the L4-L7 device being invalid for want of a concrete device), and `aci_ospf_interface_policy.ctrl` where intent emits `[]` and APIC returns `["unspecified"]`.
- **Transit-lab corrections: 4 new tools, a generator limitation lifted, and four more silent-write bugs (2026-09-16).** A review found four things unapplied. **Contracts on L3Out external EPGs**: Terraform modelled them all along but no MCP tool could write them. **A prefix in an existing match rule / a subnet in an existing external EPG**: no tool for either. **A second subnet on a bridge domain**: a real **generator limitation** — it built one BD per Prefix with exactly one subnet, and two prefixes naming one BD produced duplicate names and a Terraform "Duplicate object key". Now merged by BD name (subnets concatenate, L3Outs union, BD-level attributes take the first value so output does not depend on row order). **Eth1/4 on the leaf interface profile**: the whole access path was inexpressible — no L3-domain tool, no VLAN pool relation on `aci_l3_domain_profile`, and AAEPs could only reference *physical* domains. Closing those also fixed the standing finding that **vlan-51 was in no VLAN pool** despite BGP_L3Out using it. **Live-verified**: `15 added, 6 changed, 2 destroyed`, every object read back, fault delta **2 new and both the switch-absence family** (`F0699 Node Not Leaf`, identical to the existing one for `Host_Access_IPG`, and an `F0721` the VMM pool also carries).
- **Four more silent-write bugs, all found by using the tools (2026-09-16).** Each reported success and either wrote nothing or wrote something Terraform then rejected. **(1)** `create_access_port_selector` hit the pynautobot shallow-copy trap on location-scoped Custom Fields — fixed with `copy.deepcopy` across all six location mutators. **(2)** `create_aep` passed nested Pydantic models into a JSON field (`AepDomainSpec is not JSON serializable`). **(3)** `create_leaf_interface_policy_group` appends without deduping — three calls, three `ExtL3_IPG` entries, Terraform "Duplicate object key". **(4)** `create_contract` and `create_vlan_pool` the same. **Phase D recorded append-without-dedupe as an observation; it is a defect** — `local.*` maps in `main.tf` are keyed by name, so a duplicate does not clutter intent, it breaks the pipeline. All four fixed and guarded by tests.
- **Location is now resolved at call time, not hardcoded (2026-09-17). This was never a code bug — it was an environment divergence, and the fix matters for merging.** Eight schemas defaulted `location` to `"ACI-Lab"`, which does not exist here; this lab's Location is `Isolated Lab Site`. **The upstream repo has the same default, and there it is correct** — one of its own field descriptions reads *"this lab has one: 'ACI-Lab'"*. Two labs, two Location names, one shared codebase: **no literal default can be right for both**, which is why changing the string to `Isolated Lab Site` was rejected — it would have silently broken eight working tools upstream on the next pull. A Location name is a fact about the environment, not about the code.
  Resolution now happens in `_get_location_or_raise`: an explicit `location=` behaves exactly as before (so every upstream call is untouched); omitted, it prefers a Location already carrying `aci_fabric_policies`, uses it when unambiguous, and otherwise **raises naming the candidates rather than guessing** — writing fabric intent to the wrong site is silent and hard to spot. This keeps ACI tools unambiguous even when an unrelated project (a Catalyst Center site, say) adds its own Location, because domains are separated by **Custom Field prefix**, not by Location (EVPN already proves this: `evpn_*` fields on Devices, no Location at all).
  All 18 location-scoped tools now behave identically; three different conventions existed before (8 × `"ACI-Lab"`, 9 required, and `create_fabric_device` at `"Isolated Lab Site"`). A related cosmetic bug was fixed in the same pass: the response note echoed `request.location`, so an auto-resolved write reported **"Location 'None'"** while landing correctly — the client now returns the resolved name and the note reports it. **Live-verified over the real MCP protocol**: with no `location` argument, `create_vlan_pool`/`create_physical_domain` resolved to `Isolated Lab Site` and said so; an explicit `Isolated Lab Site` worked; an explicit `ACI-Lab` still failed as it should.

Until now those fields existed only as objects inside one running database, created by hand over several weeks; there was no answer anywhere in the repo to "what schema does this platform need?".
  **A cross-check test found real drift on the first run.** `test_the_schema_matches_what_the_platform_actually_reads` greps the generator and the MCP client for `aci_*` references and fails on any not declared. It found **12**: the VRF attribute-depth fields (`aci_ip_data_plane_learning`, both `aci_policy_control_enforcement_*`), all eight Bridge Domain attribute-depth fields (`aci_bd_mac`, `aci_bd_arp_flooding`, `aci_bd_advertise_host_routes`, `aci_bd_l2_unknown_unicast`, `aci_bd_l3_unknown_multicast`, `aci_bd_multi_destination`, `aci_bd_ep_move_detect_mode`, `aci_bd_pim`) and `aci_epg_preferred_group_member`. **None had ever existed in Nautobot.** The generator reads them, so ADR-020 Phase A's "VRF/BD attribute depth" was reachable only through hand-written fixture YAML — through Nautobot it was silently inert. All 12 now declared and created.

- **Evidence levels are now structural, not prose (2026-09-15).** CLAUDE.md always required stating `unit-tested` / `plan-verified` / `live-verified`, but nothing enforced or surfaced it, and the distinction kept being lost — most expensively when "plan-verified" was read as "works". Each `ToolSpec` now carries an `evidence` field (defaulting to the **weakest** claim, so forgetting understates rather than overstates) plus an `evidence_note` required for any `live-verified` claim. `tests/unit/test_registry.py` fails on an invalid level, a note-less live-verified claim, or drift between the registry and the counts documented here. - **APIC fault-delta verification — the missing Tier-2 check (2026-09-15).** Nothing in this platform ever looked at APIC faults, so "`terraform apply` succeeded" was silently weaker than "the configuration is valid". ## 3. Operational Hazards to Remember

These are hard-won lessons from real incidents this platform has hit — repeated here (not just in agent memory) so any reader, human or AI, sees them before touching infrastructure.

1. **Never run `docker compose down` (even with a matching `-p <project>`) from a subdirectory whose compose file is one piece of the shared `infra-automation-lab` project.** Compose reconciles *all* resources sharing that project label, not just the current file's services — this has caused two full-stack outages in this lab's history (recovered both times with zero data loss, since `down` without `-v` never deletes named volumes). Use the root `docker/docker-compose.yml` + `--no-deps <service>` for single-service work — see [`Platform-Administration-Guide.md`](../../Platform-Administration-Guide.md) §1.2.
2. **When recreating any container after an incident, cross-check GitLab's stored CI/CD project variables for that service's real credentials** before choosing placeholder values — a MinIO recovery once used different placeholder credentials than GitLab CI expected, silently breaking the `knowledge_capture` pipeline job until diagnosed.
3. **Never trust a safety hook (or any enforcement mechanism) just because it passes in isolated testing.** A `PreToolUse` hook that correctly denied a command when tested by piping JSON directly into the script completely failed to fire during a real agent run. Validate any new hook with a harmless canary command first, in the real runtime, before relying on it for anything destructive.
4. **The generator bundles ALL tenants/objects for a domain into one YAML file.** A single bad object elsewhere (a policy-violating name, a duplicate VRF) can fail `policy_check`/`terraform_plan` for the *entire* pipeline, even for changes about something unrelated. When a pipeline fails, check whether the failure is actually about what you changed before assuming a platform bug.
5. **Any generic "manage any object" Terraform resource (`aci_rest_managed` and equivalents in other providers) defaults to deleting the entire target DN/object on destroy, not just the attributes/children that resource added.** Confirmed live in ADR-020 Phase C: destroying `aci_rest_managed` resources targeting ACI's mandatory system singleton objects (`uni/fabric/time-default`, `uni/fabric/dnsp-default`, `uni/fabric/snmppol-default`) actually deleted them from the real simulator, requiring manual recreation. Fix: always set `content_on_destroy` explicitly to safe/original content when targeting a singleton object with a generic REST-managed resource — never rely on the default destroy behavior. Only caught because destroy was actually tested live, not assumed safe after a successful apply.

## 4. How to Keep This Doc Useful

> **Definition of Done — this belongs in [`CLAUDE.md`](../../CLAUDE.md) too, not only here.** The doc-update rule has historically lived only in this section, inside the very file it asks to be updated, so an agent obeys it only if it happens to open this file and read to the bottom. Between 2026-09-08 and 2026-09-12, 22 of 31 commits touched no documentation at all and the MCP catalogue silently grew from 18 to 48 tools. When you add or change a capability you must also: (1) add or extend unit tests — schema **and** dispatch for a new MCP tool; (2) record it in the relevant ADR (ADR-020 for ACI, ADR-021 for EVPN); (3) update this file; (4) update the tool catalogue in `CLAUDE.md` if you added an MCP tool; and (5) **state the evidence level explicitly and never imply more than was proven — `unit-tested` / `plan-verified` / `live-verified (apply+destroy)` are three different claims.** Point 5 is the one this vault keeps losing: treating "plan-verified" as "works" is what led to an applicable feature set being recorded as permanently blocked.

- Update this file whenever a pending item is resolved, a new one is discovered, or a real incident happens — move resolved items out of §2 (a one-line mention in §1 or a git history reference is enough; don't let this file grow into a changelog).
- Do not add live infrastructure data here (tenant counts, object IDs, pipeline numbers) — those go stale immediately and belong in Nautobot/GitLab themselves, not this vault.
- If this file conflicts with a source document (an ADR, `Execution-Framework.md`), the source document wins for design/architecture questions — this file is for status and pending work only.
