Part I — Orientation

1.1 The problem being solved

Configuring a Cisco ACI fabric by hand through the APIC GUI has three durable problems. Nobody can say later why an object exists. Nobody can reproduce the fabric from scratch. And nobody can prove the fabric still matches what was intended, six months and forty changes later.

This platform replaces GUI-driven configuration with a pipeline in which every change starts life as a structured record in a database, is transformed mechanically into configuration, is checked against policy, is approved by a human, is applied by a tool that understands state, and is then independently verified and recorded. No step is done by hand, and every step leaves an artefact.

The important design claim is that this machinery is not ACI-specific. The same pipeline already drives a second, completely different domain — Cisco Nexus VXLAN EVPN on real Nexus 9000v hardware — with no changes to any shared pipeline logic. Only domain-specific files were added. That is the platform's central proof point.

1.2 The Three Truths model

The single most useful idea in this codebase is that there are three distinct kinds of truth, and conflating them is what makes network automation projects fail. Each has a different owner, a different lifetime, and a different storage system.

TruthWhat it isWhere it livesWhy it must stay separate
1. Business Intent"The finance department needs an isolated network segment." Human-meaningful, stable, vendor-neutral.Nautobot (Tenants, VRFs, Prefixes, VLANs, plus JSON Custom Fields)Intent outlives any particular fabric. If you rebuild the fabric, intent is what you rebuild from.
2. Desired StateThe exact ACI objects that intent implies — Tenant, VRF, Bridge Domain, EPG, Contract, L3Out — expressed as data.NetAsCode YAML in Git, generated, never hand-editedIt is derived, reproducible, and diffable. A human editing it would break the chain back to intent.
3. Observed StateWhat the APIC actually reports right now, and the history of what was deployed and whether it passed verification.APIC MIT, plus Nautobot write-back fields and the MinIO knowledge logReality drifts. Only by keeping it separate can you detect the gap between intended and actual.
Why this matters when you extend the platform

Every time you add a new ACI capability, the same question decides the design: which truth does this belong to? A BGP peer's IP address is intent (truth 1). The bgpPeerP object under a specific path DN is desired state (truth 2). Whether the BGP session is actually Established is observed state (truth 3). Put a fact in the wrong truth and you will either lose it on rebuild or fight drift forever.

1.3 The ten-thousand-foot picture

A person — or an AI agent acting for them — expresses a want. That want becomes a record in Nautobot. Nautobot's change fires a webhook that starts a GitLab pipeline. The pipeline regenerates the desired state from all of Nautobot, checks it, plans it, waits for a human, applies it, configures day‑2 details, verifies it independently, writes the result back, and archives the record. Nobody touches the APIC directly at any point.

HUMAN or AI AGENT │ "create a VRF for the finance tenant" ▼ ┌───────────────┐ MCP tool call (create_vrf, create_l3out, …) │ MCP SERVER │ validates the request, writes structured objects └───────┬───────┘ ▼ REST write ┌───────────────┐ TRUTH 1 — BUSINESS INTENT │ NAUTOBOT │ Tenants · VRFs · Prefixes · VLANs · Locations │ (Source of │ + JSON Custom Fields for everything ACI-specific │ Truth) │ that Nautobot has no native object for └───────┬───────┘ │ webhook fires automatically ── the MCP Server is now out of the loop ▼ ┌──────────────────────────────────────────────────────────────────┐ │ GITLAB CI PIPELINE │ │ │ │ 1 generate Nautobot GraphQL ──▶ NetAsCode YAML (run twice, │ │ diffed, to prove determinism) │ │ 2 validate YAML is well-formed │ │ 3 policy OPA evaluates the YAML — fail-closed │ │ 4 plan terraform plan ──▶ saved plan artefact │ │ 5 apply ⏸ MANUAL GATE, then terraform apply of that plan │ │ 6 configure ansible-playbook — day-2 operations │ │ 7 verify pyATS queries the APIC independently │ │ 8 capture write results to Nautobot + append to MinIO log │ └───────────────────────────┬──────────────────────────────────────┘ ▼ ┌──────────────────┐ TRUTH 3 — OBSERVED STATE │ CISCO APIC │ └──────────────────┘

Two properties of this picture are deliberate and worth internalising:

  • The MCP Server never orchestrates. It writes to Nautobot and, separately, can read status back. It does not sequence the pipeline, does not call Terraform, and does not talk to the APIC. If the MCP Server is switched off, an engineer editing Nautobot directly gets exactly the same pipeline.
  • The generator reads everything, every time. It does not generate "just the changed object". It rebuilds the complete desired state for the domain from Nautobot on every run. This is what makes the output reproducible — and it is also the source of the platform's biggest operational hazard, covered in Part VI.

Part II — The components, and exactly what each one does

This part answers "what is each tool actually for", including the boundaries that must not be crossed. Those boundaries are the difference between a pipeline and a pile of scripts.

2.1 Nautobot — the Source of Truth

Nautobot is an open-source network source-of-truth application: a database with a web UI, a REST API and a GraphQL API, modelling tenants, VRFs, prefixes, VLANs, devices, interfaces and sites.

Its role here: it owns Truth 1. Every piece of network intent lives in Nautobot and nowhere else. Terraform variables must not contain intent. Ansible vars must not contain intent. If a fact about what the network should look like is not in Nautobot, it is not intent — it is an accident.

The interesting part is that ACI has many concepts Nautobot has no native object for: Contracts, Filters, L3Outs, Service Graphs, VLAN Pools, AAEPs. Rather than writing a Nautobot plugin with new models, this platform stores those as JSON Custom Fields attached to the nearest sensible native object. A Tenant carries aci_contracts, aci_l3outs, aci_l4l7_services; a Location carries aci_fabric_policies; a VLAN (which represents an EPG) carries aci_epg_contracts, aci_epg_domains, aci_static_paths.

This decision is both the platform's cleverest and its most fragile

It avoids a plugin and keeps everything in stock Nautobot. But a JSON Custom Field only works if the field has been declared in Nautobot's schema first. Writing to an undeclared field through the REST API does not raise an error — the value is silently discarded. That failure mode has already bitten this project once, and Part V shows it is biting again right now, at scale. See finding F‑01.

2.2 The Generator — platform/python/generate_aci.py

A ~200-line Python program plus a ~620-line transformer. It queries Nautobot over GraphQL for all tenants, prefixes, VLANs and locations, then converts that into the NetAsCode YAML structure.

Everything it does is mechanical and testable, which is why the transformer has 44 unit tests. Key conversions it performs:

  • Strips the ACI: namespace prefix that the Nautobot SSoT app adds to tenant names.
  • Derives a Bridge Domain's name from the owning Prefix's description (format ACI Bridge Domain: <bd>:<tenant>), falling back to a sanitised form of the network address.
  • Converts a Prefix's network address into a usable BD gateway host address (10.10.10.0/24 → 10.10.10.1/24), warning on stderr because this is a convention, not a fact Nautobot stores.
  • Only emits an attribute if the corresponding Custom Field was explicitly set. An unset field means "leave it at ACI's own default", which keeps generated YAML small and avoids Terraform fighting the APIC over defaults.
  • Expands the JSON Custom Fields into the nested YAML structures for contracts, L3Outs, services, fabric policies and AAA.

The pipeline runs the generator twice and diffs the two outputs. This is a real determinism gate: the generator writes YAML with sort_keys=False, so stable output depends on Nautobot returning objects in a stable order. Proving it empirically each run is cheaper than assuming it.

2.3 NetAsCode YAML — the desired-state artefact

A single file, platform/netascode/aci/tenants.yaml, holding the whole domain's desired state. It follows Cisco's Network-as-Code schema shape (apic.tenants[], apic.fabric_policies, apic.access_policies).

It is committed back to Git by the pipeline, which makes every deployment's exact input permanently auditable — you can always answer "what did we deploy on the 3rd of March" by reading a commit.

Why YAML and not a custom schema

An earlier design had the MCP Server own a "canonical intent" envelope that everything else consumed. That was deliberately abandoned. A shared intent schema becomes a second source of truth that must be kept in sync with both Nautobot and the vendor's real model — it is a permanent tax. Using the vendor-aligned NetAsCode shape means the only mapping that exists is the one the generator performs, in one place, with tests on it.

2.4 OPA — policy enforcement

Open Policy Agent runs as a container holding Rego policy files. The policy_check pipeline job posts the generated YAML to OPA and expects a {"allow": bool, "reasons": [...]} decision back.

It is fail-closed: if OPA cannot be reached, the job fails. An unreachable policy engine is treated as a denial, never as a silent pass — which is the only safe default for a guardrail.

Current ACI policy content is thin (see finding F‑08): it checks that tenant names match ^[a-z0-9-]+$ and nothing else. The EVPN policy is considerably richer, validating VNI ranges and global VNI uniqueness.

2.5 Terraform — desired-state provisioning

The module at platform/terraform/aci/ is a single 1,650-line main.tf. Its first ~570 lines are locals blocks that yamldecode the NetAsCode file and flatten its nested structure into flat maps keyed by path — "tenant/vrf", "tenant/ap/epg", "tenant/l3out/nodeprofile/ifprofile/node/module/port". The remaining ~1,080 lines are 71 resource blocks that for_each over those maps.

It consumes the YAML and nothing else. It never queries Nautobot. That separation is what lets the same Terraform run reproducibly from a committed artefact.

Two idioms recur throughout and are worth recognising:

  • lookup(each.value, "x", null) — pass null when the generator omitted a key, which leaves the attribute unmanaged at ACI's own default rather than forcing a value.
  • Relations reference another resource's .id or .name rather than the raw YAML string. This is not cosmetic: it creates Terraform's implicit dependency edge so the VRF is always created before the Bridge Domain that references it.
A hard-won safety rule encoded in this module

Several ACI objects are mandatory system singletons — the default NTP, DNS and SNMP policies at uni/fabric/time-default, dnsp-default, snmppol-default, and the fault/syslog policies under uni/fabric/moncommon. They are managed with the generic aci_rest_managed resource, whose default destroy behaviour is to delete the entire target DN. A terraform destroy once really did delete those singletons from this simulator, requiring manual recreation. Every such resource now carries an explicit content_on_destroy block resetting it to the known-good baseline. Never remove those blocks.

2.6 Ansible — Day-2 operations only

Ansible's charter here is narrow and deliberate: it performs operational tasks against already-provisioned infrastructure. It does not provision. If a playbook is creating new infrastructure, the design has been violated — that work belongs in Terraform, driven by Nautobot.

Today the ACI side runs one playbook, verify-tenants.yml, in the configure stage. The Day-2 catalogue is effectively empty (finding F‑10).

2.7 pyATS — independent verification

pyATS is Cisco's test framework. Here it connects to the APIC over REST using the rest.connector library and asserts that what the YAML said should exist actually does exist in the fabric.

The critical word is independent. pyATS does not read Terraform state and does not trust Terraform's "apply complete". It asks the APIC directly. A Terraform apply that reports success while the APIC silently rejected something is exactly the class of failure this stage exists to catch.

Current depth is shallow — it verifies that tenant names and VRF names exist, and nothing more (finding F‑09).

2.8 GitLab CI — the execution engine

GitLab CE runs locally with a registered runner. The pipeline is assembled from three files:

.gitlab-ci.ymlRoot entry point. Does nothing but include each active domain's pipeline file.
pipelines/includes/common.gitlab-ci.ymlThe shared stage templates — hidden jobs named .generate_nac, .terraform_plan, etc. All stage logic lives here and is domain-agnostic.
pipelines/aci.gitlab-ci.yml
pipelines/evpn.gitlab-ci.yml		One file per domain. Each extends the shared templates and supplies only variables: which YAML file, which Terraform directory, which policy package.

This is the structural reason a new domain is cheap. Adding Fortinet or Azure means writing a new generator, a new Terraform module and a new pipelines/<domain>.gitlab-ci.yml — and changing zero lines of shared pipeline logic.

Two GitLab CI behaviours this project learned the hard way

Included files share one flat namespace. ACI and EVPN once defined nine identically-named jobs each. GitLab does not error on this — the last included file silently overrides the first. EVPN's jobs are now all evpn_-prefixed. Likewise, top-level variables: blocks merge into one flat map, so every ACI job restates its own values via a YAML anchor to be immune to include order.

needs: is not transitive. A job only auto-downloads artefacts from jobs named explicitly in its own needs: array. write_results lists generate_nac directly for exactly this reason — without it, GitLab falls back to a plain git checkout, which can be stale relative to the artefact generated in the same run.

2.9 Vault — secrets

HashiCorp Vault holds the APIC credentials, the Nautobot API token and the vCenter credentials at secret/lab/platform. Scripts such as platform/terraform/aci/scripts/load-vault-creds.sh are sourced at job start and export TF_VAR_* environment variables, so Terraform receives credentials at runtime and never owns a static copy. The principle is that no platform component permanently stores a credential.

2.10 MinIO — the knowledge log

An S3-compatible object store. The final pipeline stage appends one JSON line per deployment to knowledge-capture/aci/deployments.jsonl. This is the durable execution history — pipeline ID, timestamp, outcome — and it is deliberately append-only and outside GitLab, so it survives pipeline retention limits.

2.11 The MCP Server

MCP (Model Context Protocol) is the standard by which an AI assistant is given callable tools. This server, at mcp-server/, exposes the platform's operations as tools an AI can invoke.

Its architecture is small and disciplined:

  • tools/registry.py — a domain-agnostic registry. It dispatches by name and knows nothing about ACI or EVPN. It must never import a domain module.
  • tools/aci.py, tools/evpn.py, tools/generic.py — domain modules that register tools via a decorator. They must never import each other.
  • schemas/aci.py — one Pydantic model per tool, defining and validating that tool's inputs. There is no shared "intent envelope"; each tool has a thin schema of exactly its own fields.
  • main.py — wires the registry into the MCP SDK, injecting the Nautobot and GitLab clients each handler declares, and building each tool's advertised input schema from its Pydantic model's fields.

Measured tool count: 46 — 42 ACI, 3 EVPN, 1 generic (show_status). Note this contradicts the project's own status document, which still says 18 (finding F‑11).

2.12 AI agents — the MCP clients

VS Code's Copilot Agent is wired as a real MCP client via .vscode/mcp.json over streamable-http. The proven milestone was a single natural-language request driving create_tenant → create_vrf → create_bridge_domain purely through tool-call reasoning, with the pipeline triggered by webhook rather than by hand.

There is also a tool-restricted persona at .github/agents/network-platform-operator.agent.md. It has MCP tools and read/search access but no terminal access — removed after an agent ran docker compose down during a live session and caused a full-stack outage. A PreToolUse hook intended to block this passed in isolated testing but did not fire during the real agent run, and the root cause was never conclusively found. Removing the capability structurally was chosen over trusting the hook. That lesson generalises: never trust an enforcement mechanism that has only been tested in isolation.

The rule for where new intent goes

If Nautobot has a native object that genuinely is the thing — use it. If ACI has a concept with no Nautobot equivalent, attach a JSON Custom Field to the nearest owning object: tenant-scoped → Tenant; fabric-wide → Location; EPG-scoped → the EPG's VLAN. Then — and this is the step that keeps being missed — declare the Custom Field in Nautobot's schema before writing to it.

3.3 Worked example: one request from end to end

Following a single change all the way through makes the machinery concrete.

1. RequestAn engineer tells the AI agent: "create a bridge domain called App_BD in the sales tenant, VRF Presales_VRF, gateway 10.0.9.254/24".
2. Tool callThe agent selects create_bridge_domain and supplies the arguments. The MCP Server validates them against CreateBridgeDomainRequest — a bad tenant name or malformed CIDR is rejected here, before anything is written.
3. Nautobot writeThe handler creates a Prefix 10.0.9.0/24 under tenant sales, assigned to VRF Presales_VRF, with description ACI Bridge Domain: App_BD:sales and Custom Field aci_gateway_ip = 10.0.9.254/24.
4. TriggerNautobot's webhook fires and POSTs to GitLab's pipeline trigger URL. The MCP Server's involvement ends here. today this only fires for Tenant changes — F‑04
5. GenerateThe generator re-reads all of Nautobot and rewrites tenants.yaml, which now contains the new bridge_domains entry with vrf: Presales_VRF and subnets: [{ip: 10.0.9.254/24, private: true}].
6. Validate + policyStructure checked; OPA evaluates the document and returns allow.
7. PlanTerraform decodes the YAML, builds local.bridge_domains["sales/App_BD"] and local.subnets["sales/App_BD/10.0.9.254/24"], and plans aci_bridge_domain.this + aci_subnet.this.
8. Approve + applyA human reviews the plan and clicks Run. Terraform POSTs to the APIC, creating uni/tn-sales/BD-App_BD and its subnet.
9. VerifypyATS queries api/class/fvTenant.json and friends and asserts presence.
10. Recordwrite_results.py stamps the tenant in Nautobot with the outcome; capture_knowledge.py appends a record to MinIO.

What a generator test looks like

Every generator test follows the same shape: build a fake Nautobot response as a plain Python dict, call build_netascode_yaml(), assert on the output structure. No network, no database, no mocking framework.

def test_bridge_domain_boolean_false_is_still_emitted_not_treated_as_unset():
    prefixes = [{
        "prefix": "10.0.0.0/24",
        "description": "ACI Bridge Domain: BD1:web-tenant",
        "tenant": {"name": "ACI:web-tenant"},
        "vrfs": [{"name": "vrf1"}],
        "_custom_field_data": {"aci_bd_arp_flooding": False},
    }]
    result = build_netascode_yaml(tenants=[...], prefixes=prefixes)
    bd = result["apic"]["tenants"][0]["bridge_domains"][0]
    assert bd["arp_flooding"] is False      # not absent — False is a real intent

That test guards a genuinely subtle bug: if cf.get("x") treats False the same as "unset", which would silently drop a deliberate "ARP flooding off". The transformer therefore uses if (v := cf.get("x")) is not None for booleans and plain truthiness for strings, and the tests pin that distinction.

What an MCP schema test looks like

@pytest.mark.parametrize("bad_name",
    ["Finance", "finance_dept", "finance dept", "Finance_2", "UPPER"])
def test_invalid_tenant_name_rejected(bad_name):
    """Mirrors the live OPA policy_check rule — catching it at the MCP
    layer avoids a guaranteed pipeline denial twenty minutes later."""
    with pytest.raises(ValidationError):
        CreateTenantRequest(name=bad_name)

Note the intent: the Pydantic schema deliberately duplicates the OPA naming rule so an AI agent is told "no" immediately rather than after a full pipeline run. @pytest.mark.parametrize is why 73 test functions produce 102 test cases.

4.3 How to add a unit test

Adding coverage for a new capability is a four-step, mechanical process. Suppose you are adding EIGRP support to the generator.

Step 1 — Write the test first, and watch it fail

Open tests/unit/test_transformer.py. Copy the nearest existing test — for a tenant-level JSON Custom Field, test_l4l7_services_emitted_from_tenant_custom_field is the right model. Adapt it:

def test_eigrp_l3out_emitted_from_tenant_custom_field():
    tenants = [{
        "name": "ACI:sales",
        "vrfs": [{"name": "Presales_VRF"}],
        "_custom_field_data": {
            "aci_l3outs": {"l3outs": [{
                "name": "EIGRP_L3Out",
                "vrf": "Presales_VRF",
                "protocol": "eigrp",
                "eigrp_as": 100,
            }]},
        },
    }]
    result = build_netascode_yaml(tenants=tenants, prefixes=[])
    l3out = result["apic"]["tenants"][0]["l3outs"][0]
    assert l3out["protocol"] == "eigrp"
    assert l3out["eigrp_as"] == 100
python -m pytest tests/unit -k eigrp -v        # must FAIL first

A test that has never failed has proved nothing. If it passes before you write the code, it is testing the wrong thing.

Step 2 — Add the negative case

Roughly half the tests in this suite assert absence. This convention exists because "only emit when explicitly set" is a core generator rule, and it is easy to break.

def test_eigrp_attributes_absent_when_not_configured():
    result = build_netascode_yaml(
        tenants=[{"name": "ACI:sales", "_custom_field_data": {}}],
        prefixes=[])
    assert "l3outs" not in result["apic"]["tenants"][0]

Step 3 — Implement until green

Edit platform/python/generator/transformer.py, re-run, iterate. Then run the whole suite — the most common real failure is that a new key changes the baseline output and breaks test_baseline_output_unchanged_when_no_custom_fields_set, which is precisely that test's job.

Step 4 — Mirror it on the MCP side

If the capability is exposed as a tool, add two more tests:

  • mcp-server/tests/unit/test_schemas_aci.py — one positive case with defaults, one parametrized negative case for invalid values.
  • mcp-server/tests/unit/test_tools_aci.py — assert the tool is registered under its exact name and calls the right Nautobot client method. The client is a hand-written fake object recording calls; no live Nautobot is involved.
The full checklist for adding any ACI capability
  1. Declare the Nautobot Custom Field — in the schema, not just in code. Skip this and writes are silently discarded.
  2. Generator test (positive) → generator test (negative) → implement in transformer.py.
  3. Add the locals flat map and resource block in platform/terraform/aci/main.tf.
  4. Add a YAML fixture under platform/terraform/aci/tests/fixtures/ and run a real terraform plan against it.
  5. MCP Pydantic schema + handler + registry entry, with schema and dispatch tests.
  6. Verify the plan actually contains the resource you expect. A clean plan is not evidence — see finding F‑09, where an OSPF fixture planned cleanly while producing zero OSPF interface profiles.
  7. Extend the OPA policy if the capability has safety implications.
  8. Extend the pyATS check so the object is actually verified after apply.

4.4 Are the tests auto-generated?

The distinction that matters is between authored and mechanically generated, not between human and AI.

There is no mechanical test generation in this repository — no snapshot/approval testing, no property-based fuzzing, no scaffolding codegen. You cannot regenerate the suite by running a command, and no test updates itself when the code under it changes. Every one of the 154 cases is an authored assertion about intended behaviour, and many were clearly written in response to a specific bug, judging by their names and docstrings (test_bridge_domain_boolean_false_is_still_emitted_not_treated_as_unset, test_l3out_trunk_mode_maps_to_provider_regular_mode).

Authorship is largely by AI agent, and that is working. The established workflow in this project — matching the parallel implementation it was developed alongside — is that the agent adding a Terraform module or an MCP tool also writes the corresponding tests in the same commit. The git history confirms the discipline holds, including in the most recent feature work:

Mechanical generation would be the wrong goal anyway: a generated test asserts that the code does what it currently does, which catches nothing. These tests encode decisions. What an AI-authored test still needs is a human confirming it encodes the intended behaviour — and it must be watched failing once before it is trusted.

Two forms of automation would nonetheless pay for themselves:

  • Fixture-driven parametrisation. Rather than one authored test per fabric-policy key, a single parametrised test over a table of (custom_field_key, yaml_path) pairs would cover all of them, and cover new keys automatically as they are added.
  • Coverage measurement. pytest --cov=generator --cov=mcp_server in CI with a floor turns "we have tests" into "we know what is untested" — a two-line pipeline change, and the highest value-per-effort testing improvement available.

Part VI — Audit findings

Ordered by the cost of leaving them alone. P1 means the platform cannot be trusted to do what it claims until this is fixed. P2 means a real defect or a material weakness. P3 means hygiene.

P1 — Must fix

F‑01The Nautobot Custom Field schema is not managed as code, and has drifted badly

The code reads or writes 36 custom-field keys. Nautobot defines 19, four of which (gbic_*) are unrelated to this platform. Missing definitions include aci_application_profile, aci_epg_preferred_group_member, the three aci_ip_data_plane_learning/aci_policy_control_enforcement_* VRF fields, all eight aci_bd_* fields, aci_vrf_route_leaks, aci_l4l7_services, aci_ospf_interface_policies, aci_aaa_policies, last_validated_at, and every evpn_* field.

I confirmed the failure mode directly: assigning an undeclared key and calling full_clean() logs "Unknown field key 'aci_l4l7_services' in custom field data" and then accepts the object. Through the ORM the value persists but is invisible to the UI and REST serializer; through the REST API — which is how every MCP tool writes — the key is dropped before it reaches the model. Either way the caller sees success.

The evidence that this has already happened: VLAN Web_EPG currently holds data under aci_application_profile, a key with no Custom Field definition. That is orphaned data from a definition that was later removed. The project's own status document records the identical bug being found and fixed once before for aci_epg_domains — which tells you it is systemic, not incidental.

Fix. Create scripts/bootstrap_nautobot_schema.py that declares every required Custom Field idempotently (key, type, content-types, description), plus the webhook. Run it in CI as a pre-flight job that fails if a required field is missing. This makes the Nautobot schema a version-controlled artefact like everything else, and converts the silent failure into a loud one.
F‑02Terraform has no remote state backend — every pipeline run starts from empty state

There is no backend block anywhere, and CI jobs run in fresh containers. terraform_plan and terraform_apply each run their own terraform init in separate containers with no shared state.

Consequences, all of which are currently masked rather than absent:

  • Every plan reports "N to add" regardless of what exists. The recurring "Plan: 27 to add, 0 to change, 0 to destroy" in the project's records is this, not a genuinely empty fabric.
  • There is no drift detection, because there is no baseline to compare against.
  • Removing intent from Nautobot never removes it from the APIC, because Terraform does not know it ever created the object.
  • The resource_group lock protects a state file that does not persist.

Fix — and the order matters. MinIO is already running and is S3-compatible, so an S3 backend is a few lines. But do not add the backend first. The pipeline currently sets ACI_TENANT_SCOPE: "sales", so the generated YAML describes one tenant. The moment Terraform has persistent state and later runs a full-scope generation — or vice versa — it will correctly propose destroying everything not in the YAML. Sequence it: (1) decide and fix the scope, (2) terraform import the existing objects into a fresh state, (3) confirm a plan reports zero changes, (4) only then wire the backend into CI.
F‑03The Nautobot Celery worker is down, so no webhook can fire

Killed by the OOM path on 10 September and never restarted. Nautobot enqueues webhook delivery as a Celery task; with no worker, nothing is delivered and nothing errors visibly. Fix: raise the container memory limit (the log shows post_upgrade being Killed), restart the worker and beat services, then confirm with nautobot-server celery inspect ping. Add a container healthcheck so this is loud next time.
F‑04The webhook covers Tenants only — 45 of 46 MCP tools trigger nothing

The single webhook is bound to Tenancy | tenant. Creating a VRF, Bridge Domain, EPG, Contract, L3Out, VLAN Pool or Service Graph writes to Nautobot successfully and then silently does not start a pipeline. The tools' own descriptions quietly admit this — "the next scheduled/triggered pipeline run will pick it up" — but no scheduled run exists either.

The Milestone 6 demonstration worked because it happened to begin with create_tenant. Any workflow that adds to an existing tenant does not.

Fix. Add the webhook content types the platform actually uses: ipam.vrf, ipam.prefix, ipam.vlan, dcim.location, and enable delete as well as create/update. Because a single business operation writes several objects, add debounce — either a short GitLab pipeline interruptible plus resource_group, or a small collector that coalesces webhooks within a few seconds — otherwise one AI request fires five pipelines.
F‑05154 unit tests exist and none of them run in CI

No pytest invocation appears in any pipeline file. The tests are excellent and cost under a second to run. Fix: add a test stage ahead of generate running both suites, and add --cov with a coverage floor. This is roughly fifteen lines of YAML and is the highest value-per-effort change available.

7.5 Options to overcome the limits

Option A — Register the discovered leaf try this first

A supported N9K-C9396PX leaf has been discovered and never registered — fabricNodeIdentP is empty. On a Cisco ACI Simulator appliance, registering discovered nodes through Fabric → Inventory → Fabric Membership (assign a node ID and name) is what brings the simulated switches into the fabric and populates fabricNode, l1PhysIf and fabricPathEp.

It costs ten minutes, is reversible by decommissioning the node, and if it works it unblocks every item this project has recorded as "permanently blocked by simulator". Given the fault explicitly says the switch has been discovered, this is worth attempting before investing in anything else. Take a configuration snapshot first. If the node registers but stays inactive with no interfaces, the appliance is APIC-only and you move to Option B.

  1. Rewrite the pyATS suite to walk the entire NetAsCode document and assert each object exists in the MIT with expected attributes.
  2. Add a fault-delta job: snapshot faultInst with type == "config" before apply, compare after, fail on new faults under managed DNs.
  3. Introduce an environment capability flag (FABRIC_HAS_NODES) that gates Tier 3/4 assertions, so the same pipeline can run against the simulator and a node-bearing fabric.
  4. Strengthen validate_nac.py with a JSON Schema and referential checks. F‑07

Phase 2 — Complete L3Out routing ~2–3 weeks

  1. Fix OSPF — correct the fixture/contract mismatch, lift area_id/area_type to the L3Out, add a test asserting the interface profile is produced. F‑09
  2. Add static routes — Custom Field entries under aci_l3outs, generator support, aci_l3out_static_route + aci_l3out_static_route_next_hop, MCP tool create_static_route, tests.
  3. Add EIGRP — same path, but via aci_rest_managed for eigrpExtP and eigrpIfP since no typed resources exist; aci_eigrp_address_family_context for the VRF side. Enforce the "not alongside OSPF on one L3Out" rule in OPA so it fails at policy, not at apply.
  4. Deepen BGP — timers, peer prefix limits, best-path policy, address-family context, route summarization.
  5. Add route control — aci_match_rule, aci_action_rule_profile, aci_route_control_profile, aci_route_control_context. Without these an L3Out cannot filter what it advertises or accepts, which rules it out for production.
  6. Apply-verify the whole physical/protocol L3Out scope. Part VII shows this will succeed. Doing it converts the largest block of "plan-validated only" into live-verified.

Phase 3 — Complete L4‑L7, PBR and Service Graphs ~2–3 weeks

  1. Add the function node — aci_function_node and aci_connection. This is the correctness fix that makes the existing Service Graph support real rather than a shell.
  2. Complete PBR — aci_l4_l7_redirect_health_group, IP SLA monitoring policy, aci_service_redirect_backup_policy, and the threshold/hashing attributes.
  3. Add concrete devices — aci_concrete_device/aci_concrete_interface, correcting the code comment that says the provider lacks them.
  4. Support two-arm and one-arm patterns explicitly, with fixtures for each, plus the symmetric-PBR case.
  5. Apply-verify the full chain: contract → graph with function node → device context → interface context → redirect policy, with the fault-delta check proving the APIC accepted it cleanly.

Phase 4 — Day‑2 operations ~2 weeks

Day‑2 is currently the weakest area relative to your goal. Terraform owns desired state; Ansible should own the operational verbs that are not state changes. Build a real catalogue:

  • Query/report — endpoint lookups, contract hit counters, interface and fault reports, health scores per tenant.
  • Operational actions — clear endpoints, decommission/recommission, enable or disable an interface, trigger an on-demand TechSupport bundle.
  • Change-adjacent — configuration snapshot before every apply and an explicit rollback runbook.
  • Troubleshooting — scripted traceroute/EP tracker equivalents driven from Nautobot intent.

Expose the safe read-only ones as MCP tools so an AI agent can answer operational questions, not only make changes. That is where most day-to-day value will come from.

Phase 5 — Closed loop ongoing

  • Scheduled drift detection — a nightly terraform plan that alerts if it is not empty. Requires Phase 0's remote state.
  • Continuous compliance — run the OPA policy set against the observed fabric, not only the desired state.
  • Restore observability — Prometheus/Grafana/Loki are documented but not running. Pipeline outcomes, fault counts and drift results are the metrics worth having.
  • Multi-fabric — once state is per-fabric, running the simulator and a node-bearing sandbox side by side gives both fast iteration and genuine verification.
If you only do three things

1. Bootstrap the Nautobot Custom Field schema as code (F‑01). Silent data loss is the worst failure mode a source-of-truth system can have, and it is happening now.

2. Add persistent Terraform state, in the safe order (F‑02). Without it there is no drift detection, no deletion, and no real convergence — the platform is an object creator, not a state manager.

3. Add the fault-delta verification job (Part VII §7.5, Tier 2). It is a day's work, it runs on the simulator you already have, and it catches the exact class of failure that "clean plan, clean apply" hides.
