Solution Comparison

Platform v2 execution framework versus the standalone ACI Nautobot lab

Comparison date: 28 August 2026

Solution A: C:\MCP\INFRA-AUTOMATION-PLATFORM

Solution B: C:\Claude Code\ACI-Nautobot\nautobot-docker, including its adjacent sales-pbr-nac automation project

Scope: Nautobot data modeling, ACI synchronization/rendering, desired-state artifacts, Terraform execution, validation, governance, auditability, extensibility, and operational cost.

Executive conclusion: Solution A is the stronger platform for repeatable, governed, multi-team automation. Solution B is the simpler and more approachable ACI lab for learning, prototyping, and manually controlled changes. They are complementary in purpose, but should not be treated as equivalent implementations.

2. Architecture and Control Flow

Solution A: Platform v2

Engineer or AI agent | v MCP Server or Nautobot UI/API | structured write v Nautobot (network desired state) | webhook: tenant change v GitLab pipeline generate -> validate -> OPA policy -> approval -> Terraform plan/apply -> Ansible Day-2 -> independent ACI verification -> result capture | | v v Git-committed NetAsCode YAML Nautobot status + MinIO JSONL evidence

The MCP server exposes narrow business-operation tools such as create_tenant, create_vrf, create_bridge_domain, create_epg, create_contract, and create_l3out. It writes structured objects to Nautobot and reads status back; it is intentionally not the pipeline orchestrator.

Relevant evidence is documented in knowledge/adr/ADR-016-NetAsCode-Centric-Execution-Framework.md, knowledge/architecture/Execution-Framework.md, platform/python/generate_aci.py, platform/python/generator/client.py, and platform/python/generator/transformer.py.

Solution B: Standalone ACI lab

Engineer | +--> Nautobot seed script or UI | | | v | Nautobot objects | +--> render_from_nautobot.py | | | v | data/generated/*.nac.yaml | +--> edit data/manual/*.nac.yaml | v terraform plan / apply | v ACI / APIC

The standalone project uses Nautobot SSoT ACI capabilities and a separate sales-pbr-nac project. Some core values are rendered from Nautobot, while policy-rich configuration remains in manually maintained YAML. The workflow is understandable and direct, but the operator must remember the correct ordering and review boundaries.

4. Nautobot-to-ACI Data Path

Solution A: deterministic generator boundary

  1. Read: platform/python/generator/client.py queries Nautobot through GraphQL for tenants, VRFs, prefixes, VLANs, and locations.
  2. Transform: platform/python/generator/transformer.py maps those objects into the ACI NetAsCode structure.
  3. Emit: platform/netascode/aci/tenants.yaml is the technology-specific desired-state artifact consumed by Terraform.
  4. Prove: the pipeline runs the generator determinism check and compares repeated output.
  5. Execute: GitLab jobs validate the YAML, evaluate OPA policy, produce a Terraform plan, require approval for apply, then run Ansible and verification.

This boundary is strong because the generator is the only translation point between Nautobot and the ACI artifact. The artifact is reviewable, reproducible, and committed to Git.

Solution B: renderer plus manual policy composition

  1. Seed: seed_nautobot.ps1 writes tenants, VRFs, prefixes, devices, and custom fields to Nautobot.
  2. Render: sales-pbr-nac/tools/render_from_nautobot.py reads Nautobot and writes generated files under data/generated.
  3. Compose: hand-maintained files under data/manual supply policy not modeled in Nautobot.
  4. Execute: the operator runs Terraform from the toolbox or host and manually reviews the plan.

This is a good lab workflow when a human is intentionally supervising each step. It is less suitable when the same change must be reproduced by different operators or promoted through environments.

6. Pros and Cons

Solution A: Platform v2

ProsCons
  • End-to-end repeatability from Nautobot change to verified execution.
  • Clear separation of desired state, execution, policy, approval, and observed state.
  • Strong governance: OPA and approval stop unsafe changes before apply.
  • Generated YAML is deterministic, reviewable, and Git-committed.
  • Supports richer ACI coverage and a second domain, EVPN, using the same mechanism.
  • MCP tools allow AI clients to request structured operations without direct APIC access.
  • Independent verification and knowledge capture make failures diagnosable.
  • High memory and CPU footprint; the documented full lab is approximately 26 GB RAM and 14 vCPUs.
  • Many services and credentials must be initialized correctly.
  • GitLab Omnibus startup and runner behavior add operational complexity.
  • Failure diagnosis spans Nautobot, webhooks, GitLab, OPA, Vault, Terraform, Ansible, and APIC.
  • Physical ACI bindings and L3Out routing are limited by the simulator, not by the software model.
  • The current clone is incomplete because its independently managed Nautobot checkout is absent.

Solution B: Standalone ACI lab

ProsCons
  • Small footprint and straightforward local startup.
  • Easy to understand for a single engineer learning Nautobot SSoT and ACI.
  • All core infrastructure runs in one focused Compose stack.
  • Manual policy YAML gives an operator immediate access to provider capabilities without first modeling every object in Nautobot.
  • Useful for experimentation and controlled proof-of-concept work.
  • Manual sequencing is easy to forget or perform out of order.
  • Nautobot and manual Git YAML jointly hold desired state, creating split ownership.
  • No automated policy, approval, independent verification, or knowledge capture.
  • Multi-tenant and broader domain expansion require script and file changes.
  • Reproducibility depends on operator discipline and local environment state.
  • Credentials are more closely tied to environment files and SSoT configuration; the documented SSoT environment variables may be deprecated in newer plugin releases.
  • Limited CI/CD and AI-client integration.

8. Recommendation

For a production-like platform or team workflow, choose Solution A. Its additional complexity buys controlled execution, policy enforcement, auditability, repeatability, and a clean path to additional domains and AI clients.

For a laptop-based ACI learning or development environment, choose Solution B. It is substantially lighter and gives an engineer a direct view of Nautobot, rendered YAML, and Terraform. It should be treated as a lab/prototype rather than the governance model for shared infrastructure.

Recommended relationship between them: use the standalone project as a lightweight ACI development or data-modeling sandbox, but promote proven patterns into Platform v2 rather than connecting both projects to the same live APIC without explicit state ownership. Do not let both Terraform roots manage the same ACI objects or use the same Terraform state.

Most important operational rule: one ACI object must have one authoritative Terraform state and one clearly owned desired-state path. Running both solutions against the same tenant, VRF, bridge domain, or policy without strict separation risks drift and competing changes.
