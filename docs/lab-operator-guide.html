2. Component Responsibility Matrix — Correcting a Common Misconception

Nautobot does not run Terraform or Ansible, and it never talks to Cisco ACI directly. This is the single most important architectural fact in this lab, so it is stated plainly before anything else: Nautobot is a Source of Truth database with a webhook, not an execution engine. Per knowledge/adr/ADR-019-Three-Truths-Principle.md: "Nautobot owns desired network state... this is Truth #2 (Desired State), not Truth #1 (Business Intent)." Execution is a completely separate concern, owned end-to-end by GitLab.

ComponentIS responsible forIS NOT responsible for
NautobotStoring Tenants/VRFs/Prefixes/VLANs as the network Source of Truth; firing a webhook when a Tenant changes; storing post-execution status (validation_status, last_pipeline_id) written back by the pipelineRunning Terraform or Ansible; deciding policy; talking to the APIC; sequencing any part of the pipeline
Generator (generate_aci.py)Deterministically translating Nautobot's live state into the ACI-specific NetAsCode YAML artifactEvaluating policy; touching ACI; deciding whether a change is approved
GitLab CE + RunnerOwning execution, approvals, retries, concurrency locking, artifacts, logs, and pipeline history for every stage — see §4 for the full listDeciding what to build (that is Nautobot + the generator's job); evaluating policy itself (delegated to OPA); verifying the result itself (delegated to pyATS)
OPAEvaluating the generated YAML against Rego policy and returning an allow/deny decision, fail-closed if unreachableTouching ACI; running Terraform; storing state
Terraform (CiscoDevNet/aci)Applying the already-planned, already-approved desired state to the real APICDeciding what the desired state should be — it only ever executes what the approved YAML/plan already says
Ansible (cisco.aci)Day-2 configuration tasks and a secondary tenant-existence sanity check after Terraform applyPrimary provisioning (that is Terraform's job); running before Terraform
pyATSIndependent, read-only REST verification against the live APIC, deliberately bypassing Terraform's own stateApplying any change — it is verification-only
MCP ServerExposing thin, per-tool business operations (create_tenant, etc.) that write structured objects straight to Nautobot, and reading status backOrchestrating the pipeline itself — per ADR-016, it "must never become another orchestration engine"
MinIODurable JSONL knowledge-capture log of every deploymentBeing any kind of configuration source
HashiCorp VaultStoring credentials read by Terraform, Ansible, pyATS, and the generatorAny decision-making role
So, concretely: Nautobot is never "acting as an IaC tool" and never "runs" Terraform or Ansible. The actual chain is Nautobot (data) → generator (translation) → GitLab (execution, running Terraform/Ansible as CI jobs) → ACI. Nautobot's only active behavior beyond storing data is firing one outbound webhook when a Tenant changes.

3. End-to-End Data Flow and Transactions

Every hop below is a real network call with a specific protocol and endpoint — nothing is implicit or in-process across these boundaries.

#From → ToProtocol / callWhat is exchanged
1Engineer / AI Agent → Nautobot (via MCP) or Nautobot UIPOST /api/tenancy/tenants/ etc., Token authA structured object write — Tenant/VRF/Prefix/VLAN
2Nautobot → GitLabNautobot's native Webhook (Jinja2 body template) → POST /api/v4/projects/:id/trigger/pipelineA pure "something changed" signal (trigger token + ref) — no object payload is sent; the pipeline re-reads Nautobot itself
3GitLab job → Nautobotgenerate_aci.py's GraphQL client → POST /api/graphql/Full current Tenant/VRF/Prefix/VLAN state, including _custom_field_data
4GitLab job → Git repositorygit commit + git push (using GIT_PUSH_TOKEN)The regenerated, deterministic tenants.yaml
5GitLab job → OPApolicy_check.py → POST {OPA_URL}/v1/data/platform/cisco_aci/decisionThe parsed YAML as input.domain_intent; response {allow, reasons}
6GitLab job → APICTerraform's CiscoDevNet/aci provider, HTTPS RESTThe planned Tenant/VRF/BD/AP/EPG/Contract/L3Out objects
7GitLab job → APICAnsible's cisco.aci collection, HTTPS REST (ansible_connection: local, no SSH)Day-2 EPG creation; a query-only tenant existence check
8GitLab job → APICpyATS' generic rest.connector, HTTPS REST GET api/class/fvTenant.jsonRead-only confirmation that expected tenants exist — independent of Terraform's own state
9GitLab job → Nautobotwrite_results.py → PATCH /api/tenancy/tenants/{id}/validation_status, last_pipeline_id, last_pipeline_url, last_validated_at
10GitLab job → MinIOcapture_knowledge.py → boto3 S3 put_object, SigV4One appended JSONL record — pipeline ID, commit SHA, operator, domain, status
11Engineer / AI Agent → Nautobot + GitLabshow_status MCP tool → Nautobot REST read + GitLab GET /api/v4/projects/:id/pipelinesMerged stored status + live pipeline status
Notice that step 2 carries no object data at all — the webhook is a doorbell, not a payload courier. Everything the pipeline needs, it re-reads live from Nautobot in step 3. This is deliberate: it means the pipeline always acts on Nautobot's current state, never on a possibly-stale webhook body.

4. GitLab's Full Role Beyond Version Control, and Its Relationship to GitHub

4.1 What GitLab actually does in this lab

Per knowledge/architecture/Platform-v2-Reference-Architecture.md: "GitLab CE + GitLab Runner own execution, approvals, retries, concurrency, resource locking, artifacts, logs, and pipeline history." Concretely, that means:

ResponsibilityGitLab-native mechanism used
Executing every stage in orderCI/CD pipeline stages + needs: job dependencies
Storing the version-controlled desired-state artifactThe Git repository itself — platform/netascode/aci/tenants.yaml is a normal tracked file
Human approval before any real changeManual job (when: manual) gated by the main branch's protected-branch rule
Preventing two concurrent applies from corrupting Terraform stateresource_group: "terraform-${POLICY_DOMAIN}-${CI_ENVIRONMENT_NAME}"
Retrying transient failuresretry: keyword on CI jobs
Preserving evidence (plans, pyATS results, logs)artifacts:, including when: always so failures still leave evidence
Being triggered by Nautobot without a human in the loopA dedicated Ci::Trigger pipeline trigger token (§13.3)
Complete execution historyPipeline list, job logs, and commit history — all queryable via the GitLab REST API

In short: GitLab is the execution engine, not just a place to store YAML. Version control is one of its jobs — orchestrating the entire Execution Framework lifecycle (Intent → Validation → Policy → Approval → Execution → Verification → Knowledge Capture, per knowledge/architecture/Execution-Framework.md) is the rest of it.

4.2 How does GitLab communicate with GitHub?

Today, it does not. This repository's own source code is version-controlled on GitHub (git remote -v confirms origin = https://github.com/panosnaz/infra-automation-platform.git) — that is where humans collaborate on and review the platform's own code, ADRs, and pipeline definitions. The self-hosted GitLab CE instance running inside this lab is a completely separate system: it is the operational execution engine that actually runs pipelines against Nautobot/APIC. There is no GitHub Actions workflow, no push-mirror, and no webhook bridge configured between the two anywhere in this repository — confirmed by a direct search of tracked files.

These two systems serve two different purposes and are not meant to be the same thing:

GitHub (github.com/panosnaz/infra-automation-platform)GitLab CE (self-hosted, in this lab)
PurposeWhere the platform's own source code is developed and reviewedWhere the generated NetAsCode YAML lives and where pipelines actually execute against live infrastructure
ContainsThis entire repository — docs, ADRs, MCP server code, pipeline definitions, Terraform/Ansible modulesA copy of the same pipelines//platform/ content, pushed in once, then modified in-place by generate_nac's auto-commits
Runs CI?No — .github/ is an intentionally empty placeholder; GitHub Actions was considered and explicitly not built (ADR-016 replaced that plan with GitLab CI)Yes — this is the only place any pipeline actually runs

If you want to connect them in the future (not implemented today)

Three honest options, in increasing order of complexity — pick the simplest one that solves a real problem you actually have, rather than adding integration for its own sake:

  1. Keep them separate (recommended default). One team, one lab — the extra synchronization complexity of connecting two Git remotes usually costs more than it saves.
  2. One-way push mirror, GitHub → GitLab. GitLab natively supports "Pull mirroring" from an external Git repository (Settings → Repository → Mirroring repositories) — GitHub stays the single place engineers push code, GitLab automatically pulls the latest pipelines//platform/ content on a schedule.
  3. GitHub Actions calling GitLab's trigger API. A workflow in .github/workflows/ could call the exact same POST /api/v4/projects/:id/trigger/pipeline endpoint documented in §13.3 whenever code is pushed to GitHub — useful only if you want GitHub pushes (not just Nautobot changes) to also trigger a GitLab pipeline run.

5. AI, MCP, and the "AI Reasons, Platform Executes" Boundary

This boundary is a first-class, named architectural decision, not an incidental detail. From knowledge/adr/ADR-010-AI-Engineering-Assistant.md:

AI provides recommendations, analysis, documentation and engineering guidance.
All infrastructure execution shall be performed by the Platform Control Plane
after appropriate validation and, where required, human approval.

  AI Recommends. Humans Approve. The Platform Executes.

AI is a platform client. It interacts with the platform in exactly the same
way as a self-service portal, a CLI, or a Jira ticket. AI never receives
privileged or direct access to execution engines.

Translated into this lab's current, actual v2 architecture (the same principle, expressed with today's real components rather than ADR-010's original, now-superseded "Platform API"/"Canonical Intent" boxes):

Nautobot UI     Jira (future)     git push     AI Agent (VS Code / Claude)     REST API
     |                |                |                    |                        |
     +----------------+----------------+--------------------+------------------------+
                                        |
                                        v
                              MCP Server (thin per-tool schemas — ADR-018)
                                        |
                                        v
                          Nautobot (structured object write)
                                        |
                                        v
                        GitLab pipeline (the ONLY thing that executes)
                                        |
                                        v
                                  Cisco ACI

Every one of those five entry points on the top row produces the same shape of Nautobot write — this is exactly why adding Jira later (§20) or a bulk LLD loader (§21) requires no change anywhere downstream of Nautobot.

The MCP Server is intentionally the only AI-facing entry point today, but it is designed to remain one of several possible front doors onto the same Nautobot data model — never the only possible one, and never itself an execution engine.

7. Step 1 — Entering Data in Nautobot

Nautobot is where you express what you want to exist. Everything downstream (NetAsCode YAML, Terraform, ACI) is derived from what you enter here — never the reverse.

7.1 The object model the generator expects

7.2 Worked example — creating one tenant end-to-end via the Nautobot UI

Step 1. Log into Nautobot (http://localhost:8081 for the isolated lab), go to Organization → Tenants → + Add.
Step 2. Name: example-tenant (matches ^[a-z0-9-]+$). Save.
Step 3. Go to IPAM → VRFs → + Add. Name: example-vrf, Tenant: example-tenant. Save.
Step 4. Go to IPAM → Prefixes → + Add. Prefix: 10.50.1.0/24, Tenant: example-tenant, VRF: example-vrf, Description: ACI Bridge Domain: example-bd:example-tenant. Save.
Step 5. Go to IPAM → VLANs → + Add. Name: example-epg, VID: 100, Tenant: example-tenant. On the custom fields section set aci_application_profile = example-ap and aci_epg_bridge_domain = example-bd. Save.

That single tenant now has everything the generator needs to emit a Tenant, a VRF, a Bridge Domain (with a subnet gateway derived from the first host of the prefix), an Application Profile, and an EPG.

8.4 Example natural-language session

You: "Create a tenant called example-tenant for the guide walkthrough."
Agent calls: create_tenant(name="example-tenant", description="Guide walkthrough tenant")
You: "Add a VRF called example-vrf to it, then a bridge domain example-bd with gateway 10.50.1.1/24."
Agent calls: create_vrf(tenant="example-tenant", name="example-vrf") then create_bridge_domain(tenant="example-tenant", vrf="example-vrf", name="example-bd", gateway_ip="10.50.1.1/24")
You: "What's the deployment status?"
Agent calls: show_status(name="example-tenant") and reports the merged Nautobot/GitLab result back to you.
The MCP Server never runs Terraform or sequences the pipeline itself (ADR-016's "never another orchestration engine" rule). It only writes to Nautobot and reads status back — the actual work is done by the webhook-triggered GitLab pipeline described in the rest of this guide.

9. Step 3 — Generating the NetAsCode YAML from Nautobot

The generator is the one and only translation point between Nautobot and the ACI-specific artifact Terraform actually consumes.

9.1 Manual invocation

# Simplest form — token via flag
python3 platform/python/generate_aci.py --url http://localhost:8081 --token <NAUTOBOT_TOKEN>

# Token via environment variable
export NAUTOBOT_TOKEN=<token>
python3 platform/python/generate_aci.py --url http://localhost:8081

# Preview only — print YAML to stdout, write nothing
python3 platform/python/generate_aci.py --url http://localhost:8081 --token <token> --dry-run

# Include ACI system tenants (common/infra/mgmt)
python3 platform/python/generate_aci.py --token <token> --include-system-tenants

# Read credentials from Vault instead of a flag
python3 platform/python/generate_aci.py \
  --vault-addr http://localhost:8200 --vault-token <VAULT_TOKEN>

Output is written to platform/netascode/aci/tenants.yaml by default (override with --output <dir>). The EVPN equivalent is platform/python/generate_evpn.py, writing to platform/netascode/evpn/fabric.yaml — same flags.

10. Step 4 — Reviewing Diffs Before Anything Is Applied

Because the generated YAML is a normal Git-tracked file, every change to Nautobot's data becomes a normal, readable git diff before it ever reaches Terraform.

+  - name: example-tenant
+    description: "Guide walkthrough tenant"
+    vrfs:
+      - name: example-vrf

10.2 Diff in the GitLab pipeline

The generate_nac job commits the regenerated YAML back to the repository automatically (with a [skip ci] commit message so it does not re-trigger itself). Review that commit exactly like any other:

# In GitLab's UI: Repository → Commits → find the "[skip ci]" commit
# Or from the CLI after a pipeline runs:
git pull
git log -1 -p -- platform/netascode/aci/tenants.yaml
Always read this diff before clicking approve on terraform_apply (§13.4) — it is the single clearest summary of exactly what is about to change on the real fabric.

11. Step 5 — Schema Validation

Before policy or Terraform ever sees the YAML, a fast structural check runs first.

python3 platform/workflows/scripts/validate_nac.py platform/netascode/aci/tenants.yaml
echo "exit code: $?"
# 0 = well-formed (has apic.tenants, every tenant has a name)
# 1 = validation failed
# 2 = usage error (wrong number of arguments)

In the GitLab pipeline this is the validate_nac job, immediately after generate_nac.

12. Step 6 — OPA Policy Enforcement

Policy is a separate question from validation: validation asks "is this technically coherent," OPA asks "is this allowed."

12.1 The actual rule enforced today

package platform.cisco_aci

default decision := {"allow": false, "reasons": ["no tenants found in domain_intent"]}

decision := {"allow": true, "reasons": []} if {
    count(invalid_tenant_names) == 0
    count(input.domain_intent.apic.tenants) > 0
}

decision := {"allow": false, "reasons": invalid_tenant_names} if {
    count(invalid_tenant_names) > 0
}

invalid_tenant_names contains msg if {
    some tenant in input.domain_intent.apic.tenants
    not regex.match("^[a-z0-9-]+$", tenant.name)
    msg := sprintf("tenant name '%s' does not match required pattern ^[a-z0-9-]+$", [tenant.name])
}

File: docker/platform-api/policy/cisco_aci/tenant_naming.rego. The EVPN equivalent additionally checks VNI range (1-16777214) and VNI uniqueness across tenants/VRFs/bridge-domains.

20. Future Integration — Jira as a Ticketing Front-Door for Day-2 Operations

Status: not implemented in this repository today. Everything below is a recommended design, built directly on principles this platform already states for itself (ADR-010's "many entry points, one execution path" and ADR-019's Three Truths model) — it is not a description of existing code.

ADR-010 already lists a Jira ticket as one of several equally valid platform clients: "It interacts with the platform in exactly the same way as a self-service portal, a CLI or a Jira ticket." The recommended pattern keeps that promise literally true.

20.1 Recommended architecture

Jira issue (type: "Network Change Request")
   custom fields: tenant, vrf, bridge_domain/gateway, epg, ticket_id
        |
        v   transitions to "Approved"
Jira Automation rule -> webhook
        |
        v
Adapter  (either: a new Nautobot Job, OR a new MCP business-operation
          tool per ADR-019's forward-compatibility note, e.g. a future
          create_day2_change_request tool)
        |
        v
Nautobot write — SAME object model as §7.1, PLUS a new
        custom field/tag: jira_ticket_id = "NETOPS-1234"
        |
        v
[ everything from §3 onward is completely unchanged ]
        |
        v
GitLab pipeline -> OPA -> Terraform/Ansible -> ACI -> pyATS -> Nautobot/MinIO

20.2 Why the ticket ID matters architecturally

ADR-019's Three Truths model names Business Intent ("why a change was requested") as a truth the platform does not yet capture explicitly — today it is implicit in commit messages and JSONL records only. Storing the Jira ticket ID as a Nautobot custom field on the affected object(s) is the simplest concrete step toward making Business Intent explicit, without inventing a new schema: every downstream artifact (the generated YAML, the Terraform plan, the knowledge-capture record) can now be traced back to the ticket that requested it.

20.3 What would need to change

  • A new Nautobot custom field, e.g. jira_ticket_id, on Tenant (and optionally VRF/Prefix/VLAN for finer-grained traceability).
  • One adapter component (Nautobot Job or MCP tool) that validates the Jira webhook payload and performs the Nautobot write — reusing the exact object model in §7.1, so the generator, OPA, Terraform, and Ansible never need to change.
  • An optional one-line addition to capture_knowledge.py's record shape (§17) — a ticket_id field — so the audit trail closes the loop back to the originating request.
Build the adapter as a Nautobot Job first (Nautobot already runs one custom Job today — the ACI SSoT sync — so the extensibility mechanism is proven in this platform) before considering a dedicated MCP tool; only add the MCP tool once an AI agent, not just Jira, also needs to originate the same kind of change.

21. Instructing Nautobot via a Low-Level Design (LLD) Document

Status: not implemented in this repository today. No "Golden Config" app, "Design Builder" app, or bulk-LLD-loading Job exists in this platform currently (confirmed by searching the codebase) — the pattern below is the recommended way to build one, consistent with how Nautobot is already extended here.

Yes, this is a good idea — but feed the LLD to Nautobot, never directly to ACI. Nautobot must remain the single ingestion point regardless of where intent originates (UI click, MCP tool, Jira ticket, or a bulk LLD file) — this is exactly what keeps the generator, policy, and pipeline unchanged no matter which front door was used, per §5's diagram.

21.1 Recommended pattern

  1. Express the LLD in a structured, versioned format (YAML, CSV, or Excel) whose fields map directly onto the object model and custom-field conventions already in §7.1 — do not invent a second, competing schema.
  2. Write a custom Nautobot Job (Python, using Nautobot's own nautobot.apps.jobs extensibility — the same mechanism this platform already uses for the Cisco ACI SSoT sync job) that: accepts the LLD file as a Job input (Nautobot Jobs support FileVar/StringVar inputs), parses it, and creates/updates Tenant/VRF/Prefix/VLAN objects and their custom fields via Nautobot's ORM.
  3. Give the Job a dry-run mode that reports what it would create/change without writing anything — mirroring the generator's own --dry-run convention (§9.1) so the same safety habit applies at ingestion, not just at generation.
  4. Run the Job via Nautobot's Jobs UI (http://localhost:8081/extras/jobs/) or its REST API: POST /api/extras/jobs/{job_id}/run/.
  5. Everything from that point is unchanged — the generator reads Nautobot exactly as it always does, and the same GitLab pipeline runs.

21.2 Illustrative Job skeleton (not existing code — a starting pattern)

from nautobot.apps.jobs import Job, FileVar, register_jobs

class ImportLowLevelDesign(Job):
    lld_file = FileVar(description="YAML low-level design document")

    class Meta:
        name = "Import Low-Level Design"
        description = "Bulk-loads Tenants/VRFs/Bridge Domains/EPGs from an LLD file"

    def run(self, lld_file):
        design = yaml.safe_load(lld_file.read())
        for tenant_def in design["tenants"]:
            tenant, _ = Tenant.objects.get_or_create(name=tenant_def["name"])
            # ... create VRFs/Prefixes/VLANs using the same custom-field
            # conventions the generator already expects (see 7.1) ...
        self.logger.info("Import complete: %s tenant(s) processed", len(design["tenants"]))

register_jobs(ImportLowLevelDesign)
This is a plain Nautobot Job doing a bulk write — not "Golden Config" and not "Design Builder" (neither is used anywhere in this platform today). Keeping it this simple means it stays a thin ingestion layer, not a second competing source of truth.

22. Future Enhancement — A LangGraph Reasoning Agent

Status: designed, not built. This section is grounded entirely in knowledge/ai/Future-AI-Integration-Design.md and knowledge/adr/ADR-019-Three-Truths-Principle.md — both explicitly describe this as a future contract, not existing code: "Explicitly out of scope until a later phase, even after this design is agreed: any Vector DB, embedding pipeline, or actual LangGraph graph/agent code. This document is the contract those future components will be built against — it does not build them."

22.1 What LangGraph would add

Quoting the design document directly: LangGraph is "the reasoning layer that combines" three sources the MCP Server does not itself combine today:

  1. Semantic retrieval from this knowledge base — architecture context, past decisions, prior incident write-ups.
  2. Structured retrieval from Nautobot — live current state.
  3. Execution history from GitLab (pipeline/job status) and the Knowledge Capture JSONL records (§17).

22.2 Where it would sit

Engineer: "Provision a new customer zone spanning ACI and EVPN,
           apply the standard security profile, and confirm compliance."
        |
        v
LangGraph reasoning agent
   1. retrieve relevant architecture/policy context from knowledge/
   2. query Nautobot for current state (avoid duplicate/conflicting objects)
   3. check GitLab + knowledge-capture history for prior similar changes
   4. decide a sequence of MCP tool calls
        |
        v
MCP Server  (same tools this guide already documents — §8)
   create_tenant -> create_vrf -> create_bridge_domain          (ACI)
   create_evpn_tenant -> create_evpn_vrf -> create_evpn_bridge_domain  (EVPN)
        |
        v
Nautobot -> GitLab pipeline -> Terraform/Ansible -> ACI/EVPN fabric (unchanged, §3)

For a single-domain, single-step request ("create a tenant"), LangGraph adds no value — the existing direct MCP tool call already handles it. It becomes useful specifically for multi-domain, multi-step business operations that today would otherwise require a human to manually sequence several separate tool calls.

22.3 What this design deliberately preserves

  • LangGraph never bypasses the MCP Server — it calls the same tools any AI agent already calls.
  • The MCP Server still never orchestrates the pipeline itself (ADR-016) — LangGraph does the multi-step reasoning, GitLab still does the multi-step execution.
  • No new write path to Nautobot is invented — every write is still one of the existing per-tool schemas (ADR-018), never a new shared "intent" object.

22.4 Recommended build order

Consistent with this platform's own proven discipline ("prove the mechanism narrow, widen later" — the same approach used to take ACI's pipeline mechanism and prove it also works for EVPN, per ADR-021):

  1. First, add real business-operation tools (e.g. a future provision_customer_zone) only once at least two matching single-domain operations already exist and are proven — today that means after both create_tenant (ACI) and create_evpn_tenant (EVPN) are in real use.
  2. Then, add semantic retrieval over knowledge/ only once a real multi-step reasoning task exists that actually needs it — not speculatively ahead of time.
  3. Only then, introduce LangGraph itself as the agent deciding tool-call order. Building the graph before there is a real multi-step business operation to justify it would repeat the exact "custom orchestration nobody needed yet" mistake ADR-016 already identified and corrected once in this platform's own history (Platform v1's custom Python orchestration, replaced by GitLab-native capabilities).

SymptomLikely cause / fix
